# Архитектура кода эпика 1

## Доменный срез и слои

`internal/document` содержит вертикальный срез операций над документами: доменную модель, прикладной сервис, HTTP-адаптер и адаптер PostgreSQL. Новые домены получают собственные срезы. Общая техника размещается в `internal/platform`, сборка зависимостей — в `internal/app`.

```text
cmd/storage → app → transport/httpapi → service → domain
                 → repository/postgres ────────→ domain
                 → assignment, platform/telemetry

Service → Repository (внедряемый PostgreSQL-адаптер)
HTTP handler → Executor (локальный адаптер / HTTP forwarding)
```

`Service` — конкретный тип. Его интерфейс `Repository` содержит Create, Get, Replace и Delete с доменными аргументами и результатом. Открытие пула, readiness, SQL и метрики не входят в контракт. Сервис не импортирует HTTP, pgx или Prometheus. Тест `internal/architecture` контролирует зависимости ядра.

HTTP DTO принадлежат `transport/httpapi`: JSON-теги, envelope, коды ответа и заголовки остаются здесь. Доменные `Key`, `Payload`, `Record` не имеют транспортных тегов. JSON-объект — часть документной модели, поэтому проверка payload входит в доменные инварианты. HTTP проверяет допустимые поля команды; сервис защищает доменные инварианты независимо от входного адаптера.

## Пример: условное обновление

1. HTTP-хендлер декодирует DTO, проверяет размер, envelope, assignment и лимит активных запросов.
2. Локальный адаптер вызывает `Service.Update` с ключом, payload и ожидаемой revision.
3. Сервис проверяет доменные значения и вызывает `Repository.Replace` без предварительного чтения и повторов.
4. PostgreSQL-адаптер получает соединение, блокирует строку, проверяет revision, заменяет payload и фиксирует транзакцию.
5. Адаптер возвращает доменную запись; HTTP-слой преобразует её в ответ.

Атомарная проверка revision — гарантия порта репозитория. Разделение проверки и записи между сервисом и БД создало бы гонку. UUID, блокировки и преобразование ошибок pgx остаются деталями PostgreSQL-адаптера. Метрики получения соединения и выполнения операции сохраняют прежние имена и labels.

## Маршрутизация и расширение

HTTP-хендлер потребляет интерфейс `Executor`: локальная реализация вызывает сервис, Router пересылает HTTP-команду владельцу один раз. Интерфейсы `Assignment` и `HTTPClient` определены у потребителя. Текущий assignment статический; интерфейс сам по себе не реализует rebalance или fencing.

Scala DSL сможет использовать API либо новый входной адаптер. Доменный сервис не зависит от способа развёртывания DSL. Control plane и динамическая публикация assignment остаются задачами следующих эпиков.

## Приложение, тесты и нагрузка

- Корневой Dockerfile собирает только `cmd/storage`; runtime содержит только бинарник приложения.
- `deploy/Dockerfile.test` запускает тесты с race detector и PostgreSQL. Тестовые файлы не входят в бинарник приложения.
- `benchmarks/load` имеет собственные `go.mod`, DTO и Dockerfile. Нет импорта кода приложения, replace-директив или прямого доступа к БД. Снимок метрик записывается через Prometheus encoder без `httptest`.
- Для hot-partition сценария клиент воспроизводит опубликованный SHA-256/modulo-128 контракт; golden test фиксирует контрольный пример. Изменение контракта требует обновления клиента.
- Внешний сценарий `benchmarks/run.ps1 -Scenario db-lock` отдельно вводит блокировку через PostgreSQL; это не функция приложения или HTTP-генератора.

HTTP API, статическая топология и схема PostgreSQL при рефакторинге сохраняются. Новые результаты производительности этим изменением не заявляются.
