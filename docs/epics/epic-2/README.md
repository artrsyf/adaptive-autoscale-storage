## Цель и границы

Эпик реализует A5 roadmap как автономный воспроизводимый harness. Он сравнивает способы отображения ключей на моделируемые вычислительные ноды при изменении состава топологии и формирует данные и графики для первого исследовательского результата.

Эпик завершён 26.09.2026. Зафиксированный исследовательский вывод и выбранный алгоритм приведены в [результатах](results.md); последующие runtime-задачи намеренно отделены.

Runtime остаётся статическим: Compose по-прежнему запускает Router и три processing unit. Harness не изменяет конфиги приложений, не запускает и не останавливает ноды, не публикует assignment, не реализует fencing и не переносит строки PostgreSQL. Потенциальный объём миграции — модель `moved keys × record bytes`, а не измеренный сетевой трафик.

## Общий контракт алгоритмов

Все стратегии реализуют `DistributionAlgorithm` из `benchmarks/partitioning/internal/distribution`. Алгоритм получает упорядоченный состав нод и необязательный предыдущий `Placement`, затем возвращает неизменяемый снимок с операцией `Owner(key)` и общими метаданными. Benchmark не знает внутреннее устройство ring или assignment и одинаково рассчитывает движение ключей и баланс.

Fixed logical partitions дополнительно возвращают список `partition → owner`. Для алгоритмов без такой модели `reassigned_partitions` неприменима и отсутствует в JSON/CSV, а не записывается как ноль. Новая стратегия добавляется отдельной реализацией интерфейса и регистрацией в `cmd/partitioning`; runner и отчёт менять не требуется.

## Сравниваемые стратегии

1. **Modulo:** `SHA-256(key)[0:8] % nodeCount`. Простой контрольный вариант; изменение числа нод обычно меняет владельца большинства ключей.
2. **Consistent hashing:** ноды представлены на hash ring настраиваемым числом virtual nodes; ключ получает следующую точку кольца по часовой стрелке.
3. **Logical partitions:** `SHA-256(key)[0:8] % partitionCount`, затем явный `assignment[partition]`. При изменении topology сохраняется максимально возможное число прежних владельцев, а итоговое число partitions на нодах отличается не более чем на одну.

Хеш ключа совпадает с контрактом Router. Идентификаторы `node-1...node-N` стабильны между исходным и целевым состояниями; scale-in удаляет ноды с наибольшими номерами, scale-out добавляет новые.

## Канонический эксперимент

Поставляемый `benchmarks/partitioning/config.yaml` задаёт:

- 1 000 000 уникальных детерминированных ключей и seed 42;
- моделируемый размер записи 1024 байта;
- 128 logical partitions;
- 128 virtual nodes на физическую ноду consistent hash ring;
- переходы `3 → 4`, `3 → 5`, `5 → 3`, `5 → 10`;
- пять повторений для временных измерений;
- пакеты по 1000 построений placement внутри каждого временного наблюдения; пакеты повторяются не менее 50 ms, затем рассчитывается средняя длительность одной операции, чтобы короткие алгоритмы не терялись на разрешении системного таймера.

Размещение и метрики движения при одинаковой конфигурации детерминированы. Повторения нужны для min/mean/median/p95/max времени; wall-clock значения зависят от машины и фоновой нагрузки.

## Метрики

- количество и доля ключей, сменивших владельца;
- моделируемый объём миграции;
- число переназначенных logical partitions, когда применимо;
- ключи на каждой целевой ноде;
- `max(node load) / mean(node load)`;
- coefficient of variation нагрузки;
- время построения исходного placement;
- время расчёта placement после изменения topology;
- время вычисления владельцев всех ключей и метрик движения.

Главная гипотеза: fixed logical partitions обеспечивают сопоставимый баланс с consistent hashing, но дают явную управляемую единицу перемещения для будущих epoch, migration state machine и load-aware placement. Результат benchmark может опровергнуть количественную часть гипотезы; отчёт не подменяет измерения реальной миграции.

## Запуск и результаты

Из корня репозитория:

```powershell
make partitioning
```

Или напрямую:

```powershell
go -C benchmarks/partitioning run ./cmd/partitioning -config config.yaml -output ../../results/partitioning
```

Каждый запуск создаёт `results/partitioning/<UTC timestamp>/`:

- `config.yaml` — фактический вход;
- `environment.json` — время, Go, ОС, архитектура и доступные VCS build settings;
- `samples.jsonl` — одно наблюдение на repetition;
- `summary.json` — агрегаты времён и детерминированные метрики;
- `comparison.csv` и `node-load.csv` — данные для внешнего анализа;
- `report.md` — читаемая таблица;
- `charts/*.svg` — moved keys, balance, CV, reassigned partitions и calculation time.

Файлы являются источником истины. Grafana не используется: это короткий категориальный эксперимент, а не наблюдение временных рядов работающего стенда.

## Критерии готовности

- общий интерфейс не содержит специальных методов конкретного алгоритма;
- одинаковая конфигурация даёт одинаковых владельцев и метрики движения;
- logical assignment полон, имеет одного владельца на partition и сбалансирован с разницей не более одной;
- `3 → 5` и `5 → 3` для 128 partitions не выполняют лишних переназначений сверх требуемых 50;
- неизвестные и некорректные настройки отклоняются;
- JSON, CSV, Markdown и все SVG создаются одним запуском;
- `make check` проходит для четырёх независимых Go-модулей.
