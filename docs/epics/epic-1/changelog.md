## Накопленный рефакторинг после e6fee76

- Router, processing unit и benchmarks/load — независимые Go-модули и Docker build contexts. Корневой бинарник `storage`, переключение роли и общий runtime-пакет исключены.
- Доменные срезы содержат модели, сервисы, потребляемые порты и адаптеры. Только Router вычисляет раздел и владельца; processing unit проверяет локальные метаданные и admission, затем вызывает DocumentService.
- Явные POST /create, /get, /update, /delete: один DocumentHttpHandler на сущность, методы операций, отдельные DTO, общие HTTP-лимиты и middleware.
- Нативные YAML-конфиги читаются потребителями; генерация инфраструктуры и HOCON удалены. Конфиги и метрики адаптеров находятся по месту использования; пароли остаются в .env.
- Имена каталогов, DNS, образов и метрик приведены к processing-unit. Заголовок X-PU-ID и ошибка pu_unavailable сохранены как wire-контракт v1.
- Имена переменных, параметров и receivers раскрыты, включая тесты и нагрузочный клиент. Правила закреплены в AGENTS.md.
- Контракты перенесены в docs/epics/epic-1; общие архитектура, roadmap и теория ВКР отделены от документов эпика. Старые результаты явно обозначены историческими.

## Маршрут для нового агента

1. Прочитать AGENTS.md, [оглавление](../../README.md), [текущую архитектуру](../../architecture.md), [API](api.md) и свежую [валидацию](validation.md).
2. Проверить `git status`, ветку и последние коммиты. Не считать незакоммиченные новые каталоги мусором; research/ и results/ — локальные игнорируемые артефакты.
3. Использовать команды из [корневого README](../../../README.md). В корне нет Go-модуля: проверки запускаются отдельно с `go -C`. Перед Docker-запуском должен быть доступен WSL2. Не удалять volumes для устранения ошибок схемы/паролей.
4. Учитывать небольшую ручную дубликацию адресов и epoch, описанную в [конфигурации](configuration.md). Изменения внутреннего HTTP-контракта проверять на обоих приложениях и независимом клиенте.
5. Следующий новый объём работ — A5 из [roadmap](../../roadmap.md): отдельный partitioning harness, сравнение modulo/consistent hashing/логических разделов с управляемым assignment. Не встраивать симулятор в серверный startup.

## Что не следует реализовывать повторно

A1–A3 уже имеют реализацию: CRUD с PostgreSQL, логические разделы и статический Router. База B1 (мониторинг) и генератор constant/ramp/burst также есть. Их развитие начинается с существующего кода и проверок, без нового универсального framework.

A4 завершён только частично: локальная проверка epoch не блокирует запись старого владельца в БД. Управляемого assignment, fencing, control plane и автоскейлинга нет. Перед динамической сменой топологии нужно определить публикацию назначений и запрет stale writes. Для автономного симулятора это не блокер. Kafka, Redis и Kubernetes не нужны для следующего partitioning-эксперимента.

Все processing units используют одну PostgreSQL: переназначение логического раздела не означает физическую миграцию строк. Потенциальный объём миграции в симуляторе и измеренный сетевой перенос должны описываться раздельно.

## Единые команды разработки

Корневой Makefile объединяет проверки трёх модулей: `make test` — Go-тесты, `make check` — форматирование/build/vet/test, `make test-all` — также контейнерные race/PostgreSQL-тесты и публичный CRUD smoke. Есть отдельные команды жизненного цикла стенда, нагрузки и отказа БД. Подробности и требования окружения — в корневом README. Нагрузочная серия и визуальная оценка Grafana не входят в test-all.

## Остаток работ и точка перехода

- `make check` выполнен успешно. Для `make test-all` проверена последовательность через `make -n test-all`; контейнерные тесты и smoke ранее выполнены отдельными командами. Единый Docker-target повторно не запускался.
- На следующем изменении запуска стенда проверить `make test-all` целиком. Отдельно остаётся проверка инициализации на новом volume, без удаления текущих данных.
- Для исследовательских выводов нужны длинные повторные серии, ramp/burst и сопоставление одной/трёх processing unit с контролем бюджета соединений и CPU. Короткие sanity-прогоны этого не заменяют.
- DB-lock подтверждён HTTP-результатами и метриками; отдельный визуальный проход этого интервала остаётся невыполненным.
- Следующий функциональный шаг — A5, автономный partitioning harness. A4 (управляемый assignment и fencing) остаётся отдельной незавершённой задачей перед динамической топологией.
- Scala DSL: способ интеграции и развёртывания не выбран. Control plane, autoscaling, Kafka, Redis и Kubernetes не реализованы и не входят в текущую проверенную поставку.

Заключительная короткая проверка: `git diff --check`, dry-run `make test-all`, синтаксис JavaScript и локальные ссылки документации. Повторная нагрузка не запускалась. Merge в master не выполнялся.
