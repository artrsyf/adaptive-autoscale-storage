Доли запросов processing-unit-1/2/3 по приращениям счётчиков между первым и последним scrape интервала: uniform **34.13% / 35.65% / 30.22%**, hot **85.72% / 6.81% / 7.47%**. При SHARE-lock на 20 секунд наблюдались **24 blocked sessions** и **24 backend в ожидании Lock**. Все 280 ошибок — HTTP 504. После прогона readiness положительный.

В hot-прогоне максимум CPU по разностям соседних scrape: генератор 0.078 ядра, Prometheus 0.013, Grafana 0.005, cAdvisor 0.058. Working set: генератор 8.1 MiB, Prometheus 119.3 MiB, Grafana 175.4 MiB, cAdvisor 49.5 MiB. В этом коротком прогоне запас ресурсов генератора и мониторинга есть; это не доказательство предельной пропускной способности стенда.

## Проверка дашборда и её границы

На сохранённом uniform-интервале **41 из 41 PromQL-запроса выполнены, пустых результатов нет**; браузерных ошибок нет. Просмотрены снимки всех пяти разделов: overview, распределение, processing units/пулы, PostgreSQL, ресурсы. Снимки и queries.json находятся в `results/branch-validation-dashboard-uniform/`. Это обзор разделов, не попиксельная проверка каждой панели. Отдельный визуальный проход DB-lock-интервала не выполнен; блокировки подтверждены архивированными метриками.

`benchmarks/check-dashboard.cjs` теперь учитывает фиксированный `to` из DASHBOARD_URL и выполняет PromQL за 5 секунд до конца интервала. Проверка только текущего времени после удаления генератора давала пустые benchmark-серии. Скрипт также снимает раздел processing units/пулов.

Короткие интервалы сопоставимы с окном rate 30 секунд: начало графиков захватывает seed/warm-up, поэтому их форма не является чистым steady-state измерением. Для исследования нужны более длинные серии, повторения, одинаковые бюджеты и интервалы после прогрева. Ramp/burst и вариант с одной processing unit в этом проходе не повторялись; новая БД на пустом volume отдельно не проверялась.

Функциональная проверка текущего статического стенда выполнена. Следующий автономный partitioning harness можно разрабатывать; численные выводы о масштабировании и завершённый fencing из этой проверки не следуют.

## Историческая нагрузочная серия — 15 сентября 2026

### Окружение и методика

Проверка 15.09.2026 (Europe/Moscow), Docker Desktop 28.0.1, Linux/WSL2: 12 CPU, около 7.6 GiB доступной памяти. Runtime серии собран из исходников `16a245a`; незакоммиченные изменения на момент серии относились к документации и проверочным скриптам. Точные image IDs и состояние дерева сохранены в каждом архиве.

PostgreSQL: 1 CPU / 768 MiB; PU: 0.5 CPU / 192 MiB; суммарный бюджет соединений — 24 как для одной, так и для трёх PU. Данные: 1024 документа, payload около 1 KiB, seed 42, warm-up 10 секунд. Это проверка функциональности и наблюдаемости, а не оценка предельной производительности или статистически значимое сравнение масштабирования.

### Нагрузочные прогоны

Перцентили в таблице вычислены по сырым завершённым HTTP-запросам измеряемой фазы, включая ошибки. Update-итерация включает GET и UPDATE, поэтому число HTTP-запросов выше числа итераций. Пропуски относятся к незапущенным итерациям и не входят в latency.

| Сценарий | PU | Итераций/с | Секунд | HTTP успешно | Конфликты | Ошибки | Пропуски | p95, мс | p99, мс |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Constant / uniform | 3 | 100 | 60 | 7253 | 0 | 0 | 9 | 5.42 | 7.51 |
| Constant / hot | 3 | 100 | 60 | 7198 | 3 | 0 | 0 | 6.56 | 17.64 |
| DB lock / uniform | 3 | 50 | 60 | 4340 | 2 | 380 | 379 | 2989.33 | 3003.37 |
| Constant / uniform | 1 | 50 | 30 | 1811 | 0 | 0 | 0 | 5.05 | 8.19 |
| Ramp / uniform | 3 | 20 → 100 | 30 | 2179 | 0 | 0 | 0 | 4.62 | 5.71 |
| Burst / uniform | 3 | 50 → 150 → 50 | 30 | 2546 | 0 | 0 | 0 | 4.96 | 6.85 |

Доля read-only итераций — 80%, кроме DB lock (20%). Скорости и длительности для одной и трёх PU различаются: эти строки подтверждают работоспособность конфигураций, а не преимущество масштабирования.

В uniform распределение по PU составило примерно **35.20% / 34.33% / 30.47%**. В hot — **87.24% / 6.71% / 6.06%**. Доли рассчитаны по приращениям счётчиков PU между первым и последним scrape измеряемого интервала.

В DB lock таблица удерживалась в SHARE-lock 20 секунд. PostgreSQL одновременно показывал **24 заблокированных backend-соединения** с ожиданием типа `Lock`; выросли задержки и появились таймауты. Генератор также достиг своего ограничения конкурентности и пропустил 379 итераций. Этот прогон демонстрирует диагностику блокировок и backpressure; его нельзя использовать как измерение throughput при полностью обеспеченной входной нагрузке.

- Go unit/integration tests с PostgreSQL и race detector.
- Публичный CRUD через Router: duplicate create, устаревшая revision, delete/recreate.
- Остановка PostgreSQL: API возвращает ошибку, readiness становится отрицательным; после запуска документ сохраняется.
- Все 41 PromQL-запроса дашборда выполняются и возвращают серии после нагрузки.

### Границы результата

Перцентили Grafana приближённые, рассчитаны по гистограммам; значения из raw summary могут отличаться. Для новых исследований нужны повторения, доверительные интервалы, одинаковые настройки сравниваемых вариантов и контроль пропусков генератора. Нет реализации динамической топологии, fencing, автоматического масштабирования, DSL, поиска по JSON и восстановления ответа при повторе операции.
