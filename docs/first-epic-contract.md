# Первый эпик: документный API и наблюдаемый локальный стенд

## Область применения

Система использует документную модель по образцу MongoDB/Elasticsearch. Этот документ определяет первый этап реализации; исходные документы описывают долгосрочную архитектуру и исследования. Совместимость с протоколами MongoDB/Elasticsearch не входит в scope.

## Модель и команды

PostgreSQL — единственное авторитетное хранилище. Запись содержит `partition_key`, `id`, `payload` (JSONB-объект), `revision`, `created_at`, `updated_at`. Идентификатор записи — пара `(partition_key, id)`. Пользовательская схема не фиксируется; служебные поля отделены от payload. Ключ маршрутизации неизменяемый.

HTTP API: POST-команды `/create`, `/get`, `/update`, `/delete` с JSON-телом. Все команды принимают `partition_key` и `id`; create/update также принимают `payload`. SQL выполняется параметризованно по фиксированным шаблонам.

| Команда | Семантика |
|---|---|
| create | Создание; существующая запись — 409 |
| get | Документ и revision; отсутствующая запись — 404 |
| update | Полная замена payload с обязательным expected_revision |
| delete | Удаление с обязательным expected_revision |

Проверка версии и изменение выполняются атомарно в PostgreSQL. Устаревшая версия — 409; некорректный запрос — 400. Успешное изменение подтверждается только после commit. Версия возвращается строкой как непрозрачный токен; повторное создание удалённой записи не должно переиспользовать старый токен. Конкретный механизм генерации выбирается при реализации.

Частичные изменения, batch, поиск по payload и многодокументные транзакции отложены. Дедупликация с сохранением ответа также отложена: потеря ответа после commit означает неопределённый результат для клиента. Автоматический повтор записи не выполняется. Проверка версии предотвращает повторное изменение старой версии, но не восстанавливает потерянный ответ.

## Архитектура стенда

`Load generator → Go Router → 3 статические Go PU → PostgreSQL`.

Предусмотреть конфигурацию с одной PU для baseline. Логические разделы определяют обработчика, а не физическое размещение строк. Фиксированное число разделов и общий статический assignment задаются конфигурацией; версия assignment отделена от revision документа. Динамический rebalance и fencing не заявляются реализованными.

Доменный срез `internal/document` разделён на модель, конкретный сервис, потребляемый интерфейс repository и адаптеры HTTP/PostgreSQL. Источник assignment отделён от бизнес-логики. Подробности: [архитектура кода](code-architecture.md). Scala DSL в будущем использует контракт операций; control plane управляет топологией и не является обязательным посредником запросов. Kafka, Redis, Kubernetes и autoscaling отложены.

## План реализации и приёмка

Реализация и проверка первого эпика описаны в [отчёте о валидации](epic-1-validation.md). Команды запуска и API — в [README](../README.md).

1. **Feature 1.1 — Document API:** Go-модуль, команды, ошибки, валидация, readiness, таймауты и graceful shutdown.
2. **Feature 1.2 — PostgreSQL Repository:** миграции, ограниченный пул, атомарные условные записи; проверки конкуренции, удаления/повторного создания и отказов БД.
3. **Feature 1.3 — Static Routing:** детерминированное разбиение, статические владельцы, проверка назначения на PU; тесты согласованности маршрутизации.
4. **Feature 1.4 — Observability:** Prometheus и автоматически настроенная Grafana; метрики Router/PU, ресурсов контейнеров и PostgreSQL.
5. **Feature 1.5 — Reproducible Workloads:** заполнение данных, constant/ramp/burst, uniform/hot-partition и воспроизводимое ограничение БД.
6. **Feature 1.6 — Local Validation:** Compose, документация запуска, интеграционные тесты, реальные прогоны и визуальная проверка дашборда.

На дашборде: заданная/достигнутая нагрузка, клиентские перцентили, ошибки и конфликты отдельно, RPS по PU и разделам, CPU/RAM, активные запросы, пул соединений, время ожидания пула отдельно от обращения к БД, соединения/ожидания/блокировки и I/O PostgreSQL. Отсутствие метрик не отображается как нулевая нагрузка. p99 узлов не усредняется.

Сохранять конфигурацию, seed, размер данных, read/write ratio, warm-up, длительность, версии, ограничения ресурсов и результаты каждого прогона. Проверять запас ресурсов генератора и мониторинга. При сравнении PU контролировать суммарный бюджет соединений. Реальные RPS/SLO определяются экспериментально; локальные результаты не обобщаются на production.

## Запуск и Git-flow

Локальный стенд запускается через Docker Compose на WSL2. Лимиты подбираются после проверки доступных ресурсов; минимальные лимиты сами по себе не доказывают репрезентативность.

Модели и контракты относятся к эпику 0 (`epic/0-foundation-contracts`). Реализация выполняется в отдельной ветке эпика 1. Коммиты содержат номер и название feature. После коммита выполняются разбор реализации и доработки по результатам ревью. Merge в `master` требует завершённых проверок и явного одобрения по итогам ревью; разрешение на реализацию или коммит не означает разрешения на merge.
